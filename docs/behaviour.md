# How it behaves

- **Addresses:** the USB adapter takes the WiFi station's MAC address, because the access point only accepts frames from it. On Linux the adapter shows up as `enx<station mac>`. The host gets its IP, gateway and DNS from your router; the MCU has none.
- **Log output:** `logTarget` selects where messages go. The library prints a few events (WiFi up/down, bridge MAC) and, if `statsIntervalMs > 0`, a status line. Nothing is printed with `LogTarget::None`.
  - `Uart0` writes to the hardware serial port `Serial0` (115200 baud). It needs no USB at all, and is the right choice on boards with a USB-UART bridge (the ESP32-P4 dev boards), whose bridge is also used for flashing. The default on the ESP32-P4.
  - `UsbCdc` adds a serial port to the USB connection, next to the network adapter. It lets the ESP32-S2/S3 be flashed without BOOT+RESET (the 1200 baud touch resets it); without it, flashing needs BOOT+RESET each time. The default on the ESP32-S2/S3.
- **Status line:** `w1 toL=.. toH=.. rf=.. dr=.. | u rx=.. tx=.. td=.. bz=.. q=.. rs=..` - `w` WiFi associated, `toL`/`toH` frames forwarded to the WiFi network / to the host, `rf` echoes dropped, `dr` frames the other side could not take, `u rx/tx` frames over USB, `td` dropped on the way out, `bz` busy polls, `q` frames queued for the host, `rs` stall recoveries. When the send queue is stuck, the status line is replaced by two `dw..` lines with the USB controller's registers (see [architecture.md](architecture.md)).
- **Stall watchdog:** if the USB send path makes no progress for `stallTimeoutMs`, the firmware drops the queued frames and disconnects/reconnects USB. The host sees this as the network card being unplugged and replugged: NetworkManager reports `carrier-changed`, restarts DHCP, and open connections break. With the USB task pinned (default) stalls are rare, so this is seldom needed; with `stallTimeoutMs = 0` a stall simply stays until you replug the board.
